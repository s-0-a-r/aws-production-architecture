# ADR-001: 3層WebシステムのアーキテクチャおよびIaC構成の選定

## ステータス
承認済み (Accepted)

## コンテキスト
AWS上で安全かつ高可用なWebシステム基盤を構築するにあたり、以下の技術的課題と制約が存在した。
1. 特定のデータセンター障害に耐えうる可用性（HA）の確保。
2. データベースパスワード等の機密情報がコードに平文混入することの防止。
3. チーム開発におけるTerraformステートファイルの競合破損防止。
4. 単一障害点（SPOF）の排除と多段防護によるセキュリティ境界の確立。
5. 個人学習環境におけるクラウド利用料の適正化（高額な常時課金リソースの回避）。

## 検討した選択肢とトレードオフ

### 1. Webサーバーの配置と外部通信経路
- **選択肢A: プライベートサブネット配置 + NAT Gateway（エンタープライズ本番標準）**
  - Webサーバーをインターネットから完全隔離し、パッケージ更新はNAT Gatewayを経由させる。
  - トレードオフ: 1AZあたり月額約45 USD（2AZで約90 USD）の時間課金が常時発生し、個人学習環境の負担が大きい。
- **選択肢B: パブリックサブネット配置 + 多段SG連鎖（採用）**
  - Webサーバーをパブリックサブネットに配置するが、インバウンドをALBのセキュリティグループIDからのみに厳格限定する。
  - トレードオフ: パブリックIPを持つが、パケットフィルタ境界で直接通信を完全拒否するため安全性を担保しつつNAT Gatewayの固定費用をゼロに抑えられる。

### 2. データベースの高可用性方式
- **選択肢A: EC2上での自前PostgreSQLクラスタ構築**
  - ライセンスや構成の自由度は高いが、OS・DBのパッチ適用やフェイルオーバーの運用負荷が極めて高い。
- **選択肢B: Amazon RDS Single-AZ + リードレプリカ**
  - 読み取り負荷分散は可能だが、非同期複製の遅延によるデータ損失リスク（RPO > 0）があり、障害時は手動昇格が必要。
- **選択肢C: Amazon RDS Multi-AZ（DBインスタンス配置）（採用）**
  - ストレージ層の同期ブロックレプリケーションとDNS CNAMEの自動切り替えにより、運用負荷を最小限に抑えつつRPOほぼゼロ・RTO 60〜120秒の自動復旧を実現。

### 3. Terraformステートの排他ロック制御
- **選択肢A: S3ネイティブロック方式（Terraform 1.10以降推奨・採用）**
  - S3の条件付き書き込み機能（`use_lockfile = true`）を利用し、DynamoDBテーブルを別途作成・管理することなくS3単体で排他ロックを完結。
- **選択肢B: DynamoDBロックテーブル方式（従来方式）**
  - 長年の実績があるが、ロック専用のDynamoDBテーブルの定義・管理が必要。

## 決定事項
1. **モジュール分割の採用**:
   単一の `main.tf` に全リソースを書く手法を排し、`vpc`、`compute_alb`、`database_rds` の3つの独立モジュールに分割した。これによりインフラの関心事を分離し、コードの可読性と再利用性を高めた。
2. **多段セキュリティグループ（SG連鎖）の採用**:
   WebサーバーおよびDBへの通信制御においてCIDR直接指定を避け、前段のセキュリティグループIDを参照元として指定した。これにより動的なIP変更に強いセキュリティ境界を構築した。
3. **RDS Multi-AZの採用**:
   EC2上に手動でDBクラスタを組む運用負荷を回避し、AWSマネージドのMulti-AZ構成を採用した。
4. **S3ネイティブロックによるリモートバックエンド**:
   ステートファイルをローカル管理せず、暗号化・バージョニング対応S3バケットと `use_lockfile = true` による排他ロックを標準採用した。

## 結果とトレードオフ
- **メリット**: 高可用性とセキュリティが確保され、誰が実行しても同じ環境を安全にプロビジョニングできる再現性を獲得した。
- **受容したコスト**: 単一AZ構成と比較して、RDSインスタンスの維持費が約2倍となる。しかし、本番水準の可用性要件を満たすためにこのコストを正当な支出として受容した。
